# 任务分解模式

本文只描述**任务切片的形状**，不改变执行模型：切片之间互不依赖时可由控制器并行派发
（受 `max_active_tasks` 与全局活跃计数约束），task group 仍不自动调度，顺序由编排者
显式选择。这些模式是「如何把一个需求切成边界清晰的 Spec」，不是「如何绕过控制器多起 Agent」。

## 先选收口方式

| 模式 | 派发 | 收口 | 前提 |
|---|---|---|---|
| 任务组交付 | `group create` → `group start`（成员在 create 时绑定） | `group accept` 一次验收 | 要的是**一次交付**；接受组内串行 |
| 独立任务并行 | 各自 `task create` + `start` | 各自 `task accept` + 人工集成 | 要的是**吞吐**；各片可独立交付 |

独立任务**不会**变成组成员（无事后绑定命令），所以「并行跑 + 组验收」不是可选路径。

## 模式零：先判断这一条能不能派发

切片的第一个问题不是"怎么切"，是"它能不能切成一个**改动**"。判据是失败形态：

| 做错时的表现 | 属于 | 派发方式 |
|---|---|---|
| 某条测试变红 / 某个 check 非 0 | 改动（W 类） | 正常派发 |
| **结论有争议**（"判 R 还是 F"、"这条算不算通过"） | 裁定（D 类） | **不派发**；写进 spec 的 `decisions`，owner 拍板（[decision-record.md](decision-record.md)） |
| 需要通读代码才能判断"到底做完了没有" | 复核（R 类） | 可派发，但只能产出报告；`allowed_paths` 不含被复核的实现文件 |

三条硬约束：

1. **裁定不是任务**：把它写成 `task create` 会让 worker 的交付物变成"一句结论"，
   而结论没有证据链、没有版本绑定，下一个人无法复核。D 类的正解是 `decisions[].status=open`
   → owner 拍板 → `task revise` 回写 `resolved`。
2. **复核不能自审**：R 类任务 `acceptance_review.independent` 必须为真。worker 在
   `DEC.md` 里写"我复核完了"不是判定——它没有 `subject_sha`、没有逐条 AC、没有证据引用。
3. **被复核的裁定文件进 `protected_paths`**：`docs/DEC.md` 一类文件一旦受保护，worker 碰它
   即 `SCOPE_VIOLATION`，该 run 不产出 candidate。这比 prompt 里叮嘱有效得多。

反例（真实事故）：把"契约冻结复核"派成一个代码任务，worker 在 `DEC.md` 里写下
"C2/C3/C4/C7/C9 判 R→F"，主进程合并了这个 PR——等于为一条没有验证过的结论背书，
而真正被它推翻的 R-10 黄金算例从未运行。

## 拆不拆：三个维度

拆不拆，看三件事；只满足"有独立 AC"并不足以拆：

| 维度 | 判断问题 | 不满足时 |
|---|---|---|
| 可独立验收 | 这一片能否定义明确的 check 与交付证据？ | 拆了也只是同一判据跑两次 |
| 可独立恢复 | 失败后能否只重跑这一片，而不是推倒整条任务？ | 拆分反而放大重跑成本 |
| 依赖与冲突 | 前后依赖能否写清、共享集成点是否可收敛？ | 先按「共享集成点」处理集成点，再谈并行 |

典型仍需拆的例子：一次数据迁移只有一个最终验收目标，但包含 schema 变更、数据迁移、
应用兼容验证三个**天然有序**的步骤 —— 依据是「可独立恢复」（失败只需重跑其中一步），
不是"有三个 AC"。

不要用「预计 15 分钟 / 50 分钟 / 代码行数」作依据：这与「不按『时长 / 行数 / 是否盯着』
路由」是同一条纪律。长跑本身不是问题，**跑完才发现没到可验收点**才是；遇到长跑先用
`timeout_seconds` 的口径（见 [runtime-contract.md](runtime-contract.md)）判断"这一次 run 的
墙钟上限"，而不是靠把任务切碎来赌。

## 使用前提（任一不满足就**分波次或按依赖串行**，不是合成一个大 Spec）

1. 下游任务的依赖已进入其基线（commit / patch / 被下游引用的结论文件）；上游「已结束」或
   「可评审」都不足以启动下游。
2. 每一片都能独立说清 AC 与可执行 check；说不出独立验收标准的只是中间态，应并入上游 Spec。
3. **运行期副作用不冲突**：共享数据库/实例、固定端口、外部服务、共享生成目录、全局缓存。
   独立 worktree 隔离的是工作区文件，**隔离不了这些**；两个任务同时跑 `docker compose up`
   或同时写 `dist/`，与 `allowed_paths` 是否重叠无关。
4. 有明确的集成本体（谁合并、按什么顺序）与独立判者。
5. 收益确实存在——仅为体现多 Agent 而拆任务是被禁止的。

`allowed_paths` / `expected_paths` 重叠是**集成风险**，不是拒绝理由：用
`group plan --project P --request-file plan.json` 只读预演看 `warnings`，再决定排两波或指定
合并顺序。不要因为它"不是硬闸"就声称"有重叠必须重切"——那两条说法互相矛盾。

两类重叠要分开看，处置完全不同：

| 重叠对象 | 性质 | 处置 |
|---|---|---|
| 普通源码路径（各片自己的模块/测试） | 集成风险 | 可并行；把"合并顺序 + 谁负责解冲突"写进本批计划 |
| **共享入口 / 注册表 / schema 索引**（`cmd/*/main.go` 的注册行、路由表、索引文件） | 结构性冲突：并行改必冲突 | 走「模式二之一：共享集成点」的 A/B，不靠"记得小心点" |

同一个文件被两片同时改，缩小 `allowed_paths` 并不能让它变安全：Worker 为了让产物可用
仍会去改集成点，而越界改动会让这次 run 以 `SCOPE_VIOLATION` 结束。别把"删掉路径声明"
当成解法。

## 模式一：调研 → 实现

先派只读调研任务把结论落成文件，再派实现任务以该结论为输入基线。

Worker prompt 骨架（调研者）：

- 角色：调研者，只读
- 目标：回答 \<具体问题\>，比较 \<候选方案 A / B\>
- 边界：可读 \<路径\>，不得修改仓库任何文件
- 产出物：\<结论文件路径\>，含结论、证据位置、被否方案及原因
- 验收：结论可追溯到具体代码或文档位置；不含无来源的表述

下游实现任务的 prompt 显式引用该结论文件，并把「遵循结论」写进 AC。

## 模式二：纵向切文件

同一特性按层次切：schema 与迁移 → API → UI，前提是三者改写的文件集合不相交。

每片 Spec 写三件事：`allowed_paths`（本片独占）、`depends_on`（已并入的上游产物）、
`verification.check_id`（来自项目批准清单）。共用迁移留在最上游那一片，
不要让两片各自生成迁移。

## 模式二之一：共享集成点（入口注册 / 路由表 / schema 索引）

同一文件是多个切片的必经改动点，并行改它必然冲突。`allowed_paths` 重叠不是拒绝理由，
但**把它从范围里删掉也不是解法**：Worker 为了让产物可用通常会改它，而越界改动会让该
run 以 `SCOPE_VIOLATION` 收场（改动留在 worktree，但不成为 candidate）。

只有两种正式模式：

| 模式 | 做法 | 适用 |
|---|---|---|
| A. 前置 scaffold（首选） | 先派一个**串行**任务，只做"入口注册 + 空实现桩"，AC 是「编译通过、既有命令不受影响」；随后并行各片只在本片包里实现，`allowed_paths` 不含入口文件 | 入口只需加注册行、各片互相独立 |
| B. 末尾接线 | 并行各片都不碰入口；合并后派一个串行任务，`allowed_paths` 只含入口文件，AC 含「新命令 `--help` 可用」+ 集成检查 | 入口改动需要看过三片产物才能确定 |

两种模式的硬条件（缺一条就把冲突推迟到验收阶段）：

1. **scaffold 形成的接口是稳定契约**：后续切片不得各自调整 scaffold；要改就回到
   scaffold 任务（新一次串行执行），不能在并行片里"顺手改一下"；
2. **接线任务必须消费已集成的上游产物**：不得在任意旧基线上执行；完成条件至少包含
   "入口可用"与"集成检查通过"，而不是只"编译通过"。

不要用"三片各自顺序追加到注册表末尾 + 约定合并顺序"当作模式：git 合并依据共同祖先与
实际差异，**不认"只追加"的约定**；三个切片从不同基点追加仍可能冲突或彼此覆盖。这只能
作为人工应急（且必须由人解冲突），不作为模式推荐。

也不要把 A/B 写成"编排者合并后手动接线"：业务代码由 Worker 实现，编排者只写
Spec/请求/报告；手写接线既不进 checks 也不进证据链。

## 共享路径计数（静态快照，不是互斥）

**共享路径要计数，不要只看"有没有重叠"**。同一个文件被 1 个候选碰是常规，被 4 个候选
同时碰就是 4 路 3-way 合并，靠"合并时小心点"必然出问题。用 digest 的 JSON 输出统计：

```bash
bash <skill-dir>/scripts/zoe-digest.sh --project P --json \
  | jq -r '.tasks[] | .task_id as $t | (.scope // [])[] | "\(.)\t\($t)"' \
  | sort | uniq -c | sort -rn | head -20
```

| 同一路径被几个候选触及 | 处置 |
|---|---|
| 1 | 正常，无需额外动作 |
| 2 | 写清合并顺序与解冲突责任人，进本批计划 |
| ≥3 | 按共享集成点处理（前置 scaffold 或末尾接线），**不要**只排合并顺序 |

计数是**静态快照**，两次统计之间状态会变（TOCTOU），它不提供互斥；也不要因为计数就要求
重切任务——重切判断依赖"这些文件会不会被同一个人改"，机器只做提示。

**两个必须写明的限制**（`prepare` 不做这件事，它不构造 Store，看不到在途任务）：

1. 这是**派发前**的静态检查，两次检查之间状态可能变化（TOCTOU）；两个编排会话同时
   检查同一路径时，都可能通过。它降低风险，**不提供原子互斥**；
2. worktree 隔离下相同路径不等天然互相覆盖；真正的冲突在候选合并、共享外部资源、
   依赖契约变更这三处。

也不要试图用 `shared_resources` 声明同一文件来换取排队：当前版本该字段只做规范化，
不产生任何串行化。

## 模式三：验证 ↔ 修复分离

跑检查的一方与改代码的一方不是同一执行，**修改方不得担任唯一的通过判据**，
否则「让测试变绿」会取代「让实现正确」。

编排者视角：

- 执行 A（实现）：产出改动与自述结果
- 执行 B（验证）：独立跑批准清单里的 checks，产出证据 ID
- 只有 B 的证据存在且绑定到 `current_evidence_id`，才进入 delivery-policy 审查

这与 recovery-policy 中「Agent 自述不等于核实成果」是同一条纪律。

## 模式四：多视角评审

把评审拆成互不重叠的关注面（安全、性能、覆盖率、接口兼容性），各派一个**只读任务**，
产出结论而非补丁。修复改动或并入新的实现 Spec，或显式 `task revise` 原 Spec。

每份评审结论必须包含：问题点、证据位置、影响面、建议修复方向——不含代码改动。

## 角色与 profile 的选择

**优先让 runtime 按任务特征选**：请求里给 `route.task_type` 与 `route.requirements`，由
`routing.rules` 与 `allowed_profiles` 决定；只有用户已明确指定执行配置时才传 `agent_profile`。

角色（实现 / 评审 / 调研）**只决定候选，不决定授权**：候选必须落在 `routing.allowed_profiles`
内，并过同一套硬条件与环境检查。声明了 `routing` 段但候选集合还没被确认时，create 返回
`ALLOWLIST_UNCONFIRMED`，见 [runtime-contract.md](runtime-contract.md)「执行配置与模型授权」。
多个角色共用一个 profile 完全正常；为了"看起来分工"给每个角色配一个模型，只会增加配置面与
未验证组合。准入仍按项目策略判定，见 [cli-contract.md](cli-contract.md)「能力与准入」。

## task / handoff / status 三件套

每个 worker 任务配套三份材料，避免上下文在续跑或换人中丢失：

| 材料 | 内容 | 对应 Zoe 命令 |
|---|---|---|
| 冻结的任务说明 | 做什么、边界、AC、允许路径 | 由 Spec 渲染，随 `task create` 冻结 |
| handoff | 做了什么、做到哪、证据在哪、下一步 | `handoff-template.md` / `task summary submit` |
| status | 当前阶段、阻塞原因、等待谁答复 | `status --refresh` / `task events` |

摘要按 `through_event_id` 绑定版本，不得覆盖控制器状态（见 SKILL.md 工作步骤第 7 步）。

## check 的验证对象自检

`checks` 的 `cwd` 是**任务 worktree**，不是仓库根。这条决定了检查结果能不能算数：

| 写法 | 实际验证对象 | 结论 |
|---|---|---|
| `["go","build","./..."]` | 任务 worktree | 有效 |
| `["bash","-c","cd /abs/repo && go build ./..."]` | **主仓库** | 假绿：并发任务构建的是同一份 main |
| `["npm","test"]` | 任务 worktree | 有效（依赖 PATH 解析） |

三条自检：

1. **命令里不要出现 `cd` 到仓库根或绝对路径**——那会把验证对象换掉，而且换掉后仍然"通过"。
2. **不要用 `bash -c` 包装**：预检只把 `bash` 判为 `shell`（`inner_command=unverified`），
   内层命令永久不可静态验证，`doctor` 的 `ready: true` 也随之失去意义。
3. **记录验证输入**：`candidate_sha`、工作树指纹、`go env GOWORK`、`go.mod` 的 `replace`
   条数。`GOWORK` 指向父目录或 `replace` 指向仓库外时，构建的未必是你以为的代码。

新增或修改 `checks` 后，先做一次**负向验证**：在 worktree 里注入一个语法错误，确认对应 check
会 `FAIL`。没有这一步，"检查有效"只是声明。

## 明确不采用的外部机制

以下来自窗格编排范式的做法与 Zoe 执行模型冲突，不予采用：

- 绕过控制器直接起多个写者并行改动同一任务：违背唯一写者与 `allowed_paths` 约束。
  （切片互不重叠时由控制器并行派发是支持的，那是 `start` 的并发准入，不是这里说的
  「手工多窗格」。）
- 手工执行 `git merge <branch>`（无论由编排者还是 worker）：Git 写操作只能由控制器
  执行，见 `runtime-contract.md`。
- 把 prompt 直接投到某个终端窗格：没有 Spec 冻结、没有 `allowed_paths` 记录、
  没有事后 diff 问责，属于「来了就跑」而非可追溯执行。
